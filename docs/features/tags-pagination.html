Tags & pagination

How tags are stored, counted, and filtered — and how paging behaves at the edges.

Tags

  • Stored on the post row: tags string[] NOT NULL DEFAULT [], GIN-indexed (index_posts_on_tags).
  • The editor lowercases and de-duplicates before saving; nothing enforces that server-side, so a console write can create Ruby and ruby as separate tags.
  • Filtering: scope :by_tag, ->(tag) { where("? = ANY(tags)", tag.to_s.downcase) } — exact match on the lowercased input, applied only when params[:tag] is present.
  • The cloud: Post.published.where.not(tags: []).pluck(:tags).flatten.tally, sorted alphabetically, returned as { tag, count }. Drafts never contribute.

Counting happens in Ruby

GET /api/v1/tags loads the tag arrays of every published post and tallies them in process. Fine for a personal blog; it is the first thing to move into SQL if the archive ever gets large.

Pagination

Parameter Default Clamping Notes
page1Non-integer or ≤ 0 → 1Offset is (page - 1) * per_page
per_page10Capped at 100, floored at 1The frontend asks for 3 on the home page and 10 on the archive

meta is returned with every list:

{ "page": 2, "per_page": 10, "total": 14, "total_pages": 2 }
  • total counts the filtered set (so it shrinks when tag is applied) and is computed before the offset/limit.
  • total_pages is (total / per_page.to_f).ceil.
  • A page past the end returns an empty posts array with valid meta — not a 404.
  • The UI hides the pager entirely when total_pages ≤ 1 and disables the edge buttons, so you cannot walk off either end by clicking.

URL behaviour

The archive keeps its state in the query string: /blog?tag=ruby&page=2. Picking a tag replaces the params (dropping page), while the pager preserves the active tag. Both are therefore bookmarkable and reload-safe.
