Docker settings

docker-compose.yml in full: three services, four volumes, and the entrypoints that make up enough.

One command

docker compose up --build      # first run, or after Gemfile/package.json changes
docker compose up              # afterwards

Then open http://localhost:5173; the API answers on http://localhost:3000. Wait for the api service to finish preparing and seeding before the first page load, or the frontend shows an error state.

Services

Service Image / build Ports Notable settings
dbpostgres:16-alpinenot publishedpostgres/postgres, database api_development, pg_isready healthcheck every 5s × 20
apibuild ./api with Dockerfile.dev127.0.0.1:3000:3000depends_on: db (service_healthy); Puma bound to 0.0.0.0:3000
webbuild ./web with Dockerfile.dev127.0.0.1:5173:5173depends_on: api; Vite started with --host 0.0.0.0

Both published ports are bound to 127.0.0.1, so the stack is not reachable from your network even on an untrusted Wi-Fi.

Environment passed in

api:
  RAILS_ENV: development
  DATABASE_URL: postgres://postgres:postgres@db:5432/api_development
  ADMIN_PASSWORD: ${ADMIN_PASSWORD:-change-me}
  JWT_SECRET:     ${JWT_SECRET:-local-development-jwt-secret-change-me}
  SITE_URL:       ${SITE_URL:-http://localhost:5173}

web:
  VITE_API_URL:   ${VITE_API_URL:-http://localhost:3000}

The ${VAR:-default} form means Compose reads the root .env (or your shell) and falls back to development defaults. Override either way:

cp .env.example .env      # then edit
# or inline:
ADMIN_PASSWORD=choose-a-password JWT_SECRET=choose-a-secret docker compose up --build

Volumes

Volume / mount Mounted at Why
./api (bind)/railsLive code reload — edits on the host take effect immediately
api-bundle/usr/local/bundleGems survive rebuilds and are not written into the bind mount
api-storage/rails/storageUploaded cover images persist across restarts
./web (bind)/appVite HMR against host files
web-node-modules/app/node_modulesKeeps container-built modules out of the host tree
db-data/var/lib/postgresql/dataDatabase persistence

Entrypoints

api — api/bin/docker-dev-entrypoint

bundle check || bundle install
./bin/rails db:prepare
./bin/rails db:seed
exec "$@"    # -> bin/rails server -b 0.0.0.0 -p 3000

So every boot installs missing gems, creates/migrates the database, and re-runs the seeds (idempotent by title — it overwrites local edits to the 14 seeded posts).

web — web/bin/docker-dev-entrypoint

Hashes package-lock.json and compares it to a stamp inside node_modules; runs npm ci only when the lockfile changed or modules are missing. That is why the second start is fast.

Images

api/Dockerfile.dev is ruby:3.3.6-slim plus build-essential git libpq-dev libvips libyaml-dev pkg-config postgresql-client, with BUNDLE_PATH=/usr/local/bundle. web/Dockerfile.dev is node:20-slim with npm ci at build time. api/Dockerfile (no .dev) is the stock Rails production image and is not used by Compose.

Goal Command

Rubocopdocker compose exec api bin/rubocop
psqldocker compose exec db psql -U postgres api_development
Reseeddocker compose exec api bin/rails db:seed
Reset everything (destroys data)docker compose down -v
Rebuild after dependency changesdocker compose up --build
Frontend lintdocker compose exec web npm run lint

This compose file is a development convenience: source is bind-mounted, secrets default to change-me, RAILS_ENV=development, and the frontend runs the Vite dev server rather than a build. Never point it at anything public — see Production readiness.
