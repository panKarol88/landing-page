Production readiness

What is ready, what is missing, and the concrete list of things to change before this is public.

What exists

  • api/Dockerfile — the stock Rails 8 production image (precompiled bootsnap, non-root user, Thruster in front of Puma).
  • api/config/deploy.yml and api/.kamal/ — Kamal scaffolding with sample hooks, still carrying placeholder values.
  • api/config/environments/production.rb — stock settings, including force_ssl and log-to-stdout behaviour from the generator.
  • npm run build — produces a static web/dist/ bundle ready for any CDN or static host.
  • GET /up — a health endpoint a load balancer can poll.

A minimal path to public

  1. Pick hosting for two artifacts: the Rails image and the static web/dist.
  2. Add the real frontend origin to the CORS allowlist, and serve both over HTTPS.
  3. Provision Postgres with backups; set DATABASE_URL and RAILS_MASTER_KEY.
  4. Set strong ADMIN_PASSWORD and JWT_SECRET, plus the real SITE_URL, as deploy-time secrets — never in git.
  5. Point Active Storage at durable storage (bucket or mounted volume).
  6. Build the frontend with VITE_API_URL set to the public API URL.
  7. Wire /up into the platform's health checks and add error reporting.
  8. Decide on SEO: if it matters, prerender or move to a framework that can.

Until all of the above is done, treat this as a local-only application. The current defaults (change-me, localhost CORS, disk storage, dev server) are safe precisely because nothing is exposed — both published ports bind to 127.0.0.1.
