Design decisions

The choices baked into the code, and the reasoning — including the ones worth revisiting.

One shared password instead of user accounts

There is exactly one author, so there is no users table, no registration, and no password reset. POST /api/v1/session compares the submitted password to ENV["ADMIN_PASSWORD"] using ActiveSupport::SecurityUtils.secure_compare over SHA-256 digests (constant length, constant time) and issues a JWT. Consequence: rotating the password is an env-var change and a restart, and there is no way to revoke a single token other than changing JWT_SECRET.

Stateless JWT instead of a server session

The API stores nothing about logins. A 7-day HS256 token in localStorage keeps the API free of session storage and lets the SPA live on a different origin without cookie/CSRF plumbing. The trade-off is real: a token cannot be invalidated individually, and localStorage is readable by any script that manages to run on the page.

Slugs as the public identifier

Routes use param: :slug, so URLs are /api/v1/posts/a-slugged-post and /blog/a-slugged-post — no integer IDs leak, and the URL is readable. The slug is generated from the title with parameterize on create and de-duplicated with a -2, -3… suffix. Renaming a slug changes the public URL and leaves no redirect behind.

Tags as a Postgres array, not a join table

posts.tags is string[] NOT NULL DEFAULT [] with a GIN index. Filtering is where("? = ANY(tags)", tag.downcase) and the tag cloud is computed in Ruby with pluck(:tags).flatten.tally. For a single-author blog this removes two models and a join; it also means there is no tag rename, no tag description, and the cloud is computed on every request.

published_at is stamped once, never overwritten

before_save :sync_published_at uses self.published_at ||= Time.current if published?. Unpublishing and republishing a post therefore keeps its original date, so the archive ordering does not jump around when you fix a typo. Two integration tests pin this behaviour.

Markdown stored raw, rendered in the browser

The database keeps body_markdown; the API never returns HTML. The SPA renders it with react-markdown + remark-gfm + rehype-highlight, which also powers the editor's live preview with zero server round-trips. The one place the server renders Markdown is the RSS feed, where Redcarpet runs with filter_html: true.

Four full themes instead of a colour switch

Each theme (Notion, Brutalist, Pixel, Neon) provides its own Shell, Hero, TagCloud, PostList, PostCard, and ReaderChrome components plus a block of CSS variables. Tailwind's palette is mapped onto those variables (bg, surface, fg, accent, rounded-theme, shadow-card…), so page code stays theme-agnostic and a new theme is one folder plus one registry entry.

No SSR, no static generation

The site is a client-rendered SPA. That keeps the stack small but means crawlers and social previews see an empty shell, and a cold visit waits for the API. This is the main open architectural decision if the blog ever needs SEO.

Uploads validated by magic bytes

UploadsController ignores the browser-supplied content type and sniffs the first 16 bytes to accept only PNG, JPEG, GIF, and WebP, with a 5 MB cap. SVG is rejected on purpose — it can carry script. A test uploads an SVG labelled image/png and asserts a 422.

Profile in YAML, not in the database

GET /api/v1/profile reads api/config/profile.yml on every request, so name, headline, bio, avatar, location, links, and skills are edited in git with no migration and no admin screen.

Docker for development only

docker-compose.yml binds both ports to 127.0.0.1, ships change-me defaults, mounts the source read-write, and runs db:prepare/db:seed on every boot. It is a convenience wrapper for one machine, explicitly not a deployment artifact — production would use api/Dockerfile and a real build of web/.
